Chaîne d'acteurs

Trois parties distinctes. Nous ne parlons jamais directement à l'utilisateur final — seul le logiciel de l'éditeur le fait.

1

Plateforme (nous)

Provisionne les comptes éditeur via /platform/*, détient le X-Platform-Token.

→
2

Éditeur (tenant)

Reçoit ses tokens, gère ses licences via /admin/*, fixe le quota "X licences / utilisateur".

→
3

Logiciel de l'éditeur

Jeu, app, SaaS — embarque le X-Client-Token de l'éditeur, appelle /activate.

→
4

Utilisateur final

Client de l'éditeur, pas de nous. Reçoit une licence, la saisit dans le logiciel pour le débloquer.

Qui l'utilise

Cibles — les éditeurs

Tout éditeur capable d'appeler une API HTTPS peut consommer ce service de licences de la même façon. C'est leur logiciel qui parle à l'API — leurs utilisateurs finaux, eux, ne voient qu'un champ "entrez votre clé de licence".

Ce que fait l'API

Capacités principales

Cinq choses que l'on peut faire avec cette API — le reste (quotas, sécurité) découle de ces actions.

Platform

Provisionner un éditeur

Nous créons le compte d'un éditeur : il reçoit un token client et un token admin, générés une fois.

POST /platform/publishers
Client

Activer une licence

Le logiciel de l'éditeur envoie l'email et la clé saisis par l'utilisateur final ; l'API vérifie le quota d'appareils (X par utilisateur) et renvoie un token signé.

POST /activate
Client

Libérer un appareil

Quand l'utilisateur final change de machine, un appel libère le slot d'activation pour le réutiliser ailleurs.

POST /deactivate
Public

Vérifier hors-ligne

Le logiciel récupère la clé publique active (par kid) une fois, puis vérifie la signature du token localement, sans rappeler le serveur.

GET /public-keys
Admin

Administrer ses licences

L'éditeur crée, liste, active/désactive ses propres licences et peut forcer la désactivation d'un appareil.

/admin/*

Prise en main — côté éditeur

Comment un éditeur intègre l'API

Le chemin le plus court entre la création de votre compte éditeur et une fonctionnalité débloquée chez votre utilisateur final.

1

Recevoir vos identifiants

Un X-Client-Token et un X-Admin-Token, générés une fois lors de la création de votre compte éditeur.

→
2

Intégrer /activate dans votre logiciel

Avec l'email et la clé de licence saisis par votre utilisateur final, plus un identifiant d'appareil.

→
3

Stocker le token signé

La réponse contient les métadonnées de licence, un kid, et une signature Ed25519.

→
4

Vérifier hors-ligne

À chaque lancement, comparer la signature à la clé publique correspondant au kid — aucun appel réseau requis.

Sécurité — ce qui vous protège

Rien en clair

Les clés de licence ne sont jamais stockées : seul un hash HMAC-SHA256 salé (pepper) est comparé.

Signatures vérifiables hors-ligne

Chaque token est signé Ed25519 ; le logiciel client le vérifie localement, sans dépendre du serveur à chaque lancement.

Jetons d'accès séparés

Un jeton client (X-Client-Token) et un jeton admin (X-Admin-Token) distincts, jamais mélangés.

Débit limité par utilisateur final

/activate est throttlé par (éditeur, email) — pas seulement par jeton d'éditeur partagé. Un utilisateur qui teste des clés au hasard ne peut ni se cacher dans, ni bloquer, le trafic des autres utilisateurs du même éditeur.

Fenêtre de validité limitée

Un token expire par défaut au bout d'1h (expires_at). Passé ce délai, le logiciel rappelle /activate — ce qui capte une éventuelle révocation côté serveur. Le hors-ligne n'est donc jamais permanent.

Clé de signature avec rotation & sauvegarde

La clé Ed25519 vit en base (pas seulement dans un fichier) : elle est donc sauvegardée avec le reste des données, et peut être remplacée sans invalider les tokens déjà émis — chaque token porte le kid de la clé qui l'a signé.
