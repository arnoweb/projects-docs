MUSÉE DU LOUVRE // ARCHITECTURE

The redesign of louvre.fr: a headless Drupal back office that serves a JSON API, a Next.js engine that renders the pages, three managed environments and a release shipped at the end of each sprint.

Headless CMS Drupal 8 Next.js · React Node.js · PM2 Varnish Redis Elasticsearch MariaDB Cloudinary GitLab CI/CD

The project

The Louvre decided to rebuild louvre.fr from the ground up: new application layer, new infrastructure. Mazarine Digital won the public tender for the redesign and its maintenance. I led the technical side: the architecture, the technical file shared with the museum and its hosting provider, the delivery pipeline and a team of 6 people.

The site serves tens of millions of page views a year, with peaks around the major exhibitions. It has to be fast everywhere, accessible to every visitor and easy to edit for the people who publish on it every day.

Editors first

37 contributors in 6 departments publish exhibitions, events and visitor information. The back office gives each role access only to the fields it needs.

Fast pages, indexed pages

Pages are rendered on the server for search engines and first load, then the site navigates like an app. Two cache layers sit in front of the application.

Accessible by design

Target: RGAA 4, level AA. Each component is reviewed with an accessibility expert from the design stage, before it is coded.

Ready for other channels

Content lives behind an API, not inside page templates, so a mobile app or a partner service can use the same content later.

Why headless

A classic CMS renders its own pages: the editing tool and the public site are one system. We split them in two. Drupal manages content and exposes it as a JSON API. Next.js consumes that API and renders the site.

CriterionClassic CMSHeadless (chosen)
Any device or channelNoYes, through the API
Front and back can change technologyNoYes, the API contract is the only link
Upgrade the CMS without touching the siteNoYes
Front and back maintained on their ownNoYes, two repositories, two teams
Fits short agile iterationsPartlyYes

The trade-off: editors lose the native page preview of a coupled CMS. We rebuilt it, so a contributor can still see a draft as it will look on the site.

The layers

01
Front: Next.js on Node.js
React components rendered on the server for the first load and for search engines, then client-side navigation between pages. The front calls the API both from the Node.js server (SSR) and from the browser. PM2 keeps the Node.js processes alive. Components are built and reviewed in Storybook.
02
Back office: headless Drupal 8
Drupal handles editing, roles, translations and SEO fields, and exposes everything as REST services in JSON. The API contract is documented in Swagger, so front and back can work in parallel. Cron runs the background jobs, such as imports from the collections feeds.
03
Edge: load balancer, Varnish, Nginx
HTTPS and HTTP/2 end at the load balancer. Varnish caches HTML pages and API answers. Nginx routes to the right application, with HTTP/2 and Brotli compression.
04
Data: MariaDB, Redis, Elasticsearch
MariaDB as the relational database, Redis as a key/value cache in front of it, Elasticsearch for search and instant suggestions. All three run as primary/replica, on SSD storage.
05
Media: Cloudinary and YouTube
Drupal uploads images and PDFs to Cloudinary, which resizes them for each device and serves them from several CDNs. The front only builds the URLs. Videos are hosted on YouTube.

Deployment pipeline

The agency builds, the host installs. Our GitLab CI jobs compile each application and push a tagged, ready-to-run release to the host's Git. The host's deployment script then installs it on the target environment.

FIG. 3 · Build once at the agency, install the same release on every environment.
  • Every install is a full install. Nothing is patched in place.
  • A release goes live only once it is fully installed, by switching a symbolic link. Rolling back is switching it back.
  • Code, media and database travel separately. Media stays on storage shared by all servers.
  • The release number is collected by the deployment tool and hidden in the HTML, so anyone can check what runs where.
  • No production release on a Friday.

Git Flow, one release branch per sprint

The sprint review decides what happens to the release branch. The rule was agreed with the museum before the first review:

100% VALIDATED
Ship it

The release branch is merged into master and tagged. It goes to production.

OVER 80%
Fix on the release

Fixes go on the release branch, are tested again, then merged into master (tagged) and back into develop.

UNDER 80%
Back to develop

Fixes go on develop or on the feature branches, and a new release branch is cut for a new round of testing.

Performance

Performance was a requirement from the first sprint, measured with Lighthouse on every release: time to first byte, first contentful paint, Speed Index (target under 1,000), time to interactive and full load.

01
Cache what can be cached
Generated HTML and API answers in Varnish, data in Redis, images resized and served by a CDN, CSS and JavaScript split per component and loaded on demand.
02
Load tests during the sprints
Load test scenarios on the API and the front, written with the museum and run on the production platform before launch, while the host watched the infrastructure. Capacity problems show up during development, not at launch.
03
Real devices
A device lab of 24 phones, tablets and computers, plus BrowserStack, so the site is also tested on slow hardware.

A cache header that said two things

During the setup, the application sent this header:

before Cache-Control: s-maxage=10800, private, max-age=0, must-revalidate after Cache-Control: s-maxage=10800, public, max-age=0

s-maxage asked the shared cache (Varnish) to keep pages for 3 hours, but private told it not to store them at all. And must-revalidate meant that if the back end stopped answering, visitors would get an error page instead of the last good copy. The fix keeps 3 hours in Varnish, nothing in the browser, and lets Varnish serve a stale page when it has to.

LESSON One routing setup per environment. Acceptance had no Varnish, so the load balancer could not route it like pre-production and production: it had to go through Nginx. We drew the routing for each environment before going further.

Accessibility

The museum asked for RGAA 4, level AA. The work starts before any code:

01
Design review
An external accessibility expert reviews the designs against each RGAA criterion and flags problems while they are cheap to fix.
02
Component specs
For each component, the expert describes how it must be built to stay accessible. Developers follow these specs and can ask the expert directly.
03
Audit and statement
Checks with WAVE and Tanaguru during development, then an audit and the accessibility statement required by law.

Operations

Shared responsibility

A RACI split each task between the museum, the agency and the host: sizing, certificates, backups, CI/CD, load tests, content migration, monitoring.

Managed hosting

The host runs systems, network and monitoring, 24/7 on production, with weekly full and daily incremental backups.

Locked-down access

Acceptance and pre-production are reachable from an IP allowlist only. So is the production back office. One wildcard certificate covers all subdomains.

Maintenance

After launch, the platform moved to quarterly release cycles, mixing new features, fixes and upgrades in the same sprints.
