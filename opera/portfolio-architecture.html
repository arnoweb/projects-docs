OPÉRA NATIONAL DE PARIS // ARCHITECTURE

operadeparis.fr: a Laravel platform with its own back office and public API, tied minute by minute to the Opéra's ticketing system, and maintained release after release for seven years.

Laravel · PHP Twig Native JS · TypeScript Secutix ticketing SAML SSO Varnish MariaDB · Redis Elasticsearch Cloudinary k6

The platform

The Opéra national de Paris runs two venues, the Palais Garnier and the Opéra Bastille, and sells its seasons, subscriptions and tours online. operadeparis.fr is where the public discovers the programme and starts every purchase. At Mazarine Digital I led its technical direction from 2018 to 2025, with a team of 6 people, under a maintenance and evolution contract with quarterly releases.

The site is made of three parts, all built on Laravel:

WWW
Front end

Server-rendered pages with Twig, and a framework-free front end in native JavaScript and TypeScript.

ADMIN
Back office

The Opéra's teams edit shows, pages, the magazine and the settings of features such as seat alerts.

API
Opéra API

Selected content exposed in JSON for the Opéra's mobile app, the patrons' website and partner sites.

TICKETING
Secutix, outside the platform

Catalog, seats, customer accounts, cart and payment live in Secutix, a ticketing SaaS. The site depends on its web services at every step.

Seats on the show page

A show page lists its performances, and for each one, the seat categories with their price and availability. A category with no seats left stays visible and turns grey. When a whole performance is sold out, a message replaces the categories.

01
Catalog sync
Every 15 minutes, a cron reads the season catalog from Secutix (shows, performances, categories, prices) and stores it in the site's database.
02
Availability sync
Every minute, another cron reads the seats left per category and per performance. Only one run at a time is allowed. These numbers change too often to be shown in the back office.
03
Seat alerts
The same cron sends the alert emails. An email goes out when seats go above a threshold, if the performance is at least 2 hours away and if the visitor has not already been alerted. Emails leave in batches, every 15 minutes by default, so the mail server is not flooded. The threshold, batch size and interval are set in the back office.

One login for the site and the ticketing

Accounts live in Secutix. The site and the ticketing run on different subdomains, and visitors must not have to log in twice.

FIG. 3 · The site logs in on the visitor's behalf, then hands the ticketing session over through a parent-domain cookie.
WHAT BROKE FIRST Secutix sets its session cookie on its own subdomain. A visitor who logged in on the site arrived on the ticketing as a stranger. The fix: the site runs the SAML exchange from the server, reads the session cookie from Secutix's response headers, and sets it again on the parent domain, where both sites can read it.

Facebook login follows the same path with a few more calls: find the contact by its social identifier, create it or link the social account if needed, then authenticate. Sign-up itself is a form hosted by Secutix, with one flow for individuals and another for groups, each with its own contact base.

Living with a rate limit

In early 2023, after a cyberattack took down another major opera house's ticketing, Secutix put a per-minute limit on its web services. That limit is shared by operadeparis.fr, the Opéra's streaming platform and its Aria web app. Above it, pages that need ticketing data start to fail.

01
Map every call
A note for the Opéra listing every web service call of the three sites: which service and version, when it runs (cron, login, sign-up, profile), with which parameters and why.
02
Measure
Error tracking first, then the Opéra's own monitoring of the calls, to see which journeys consumed the most.
03
Cut
Read from the database or the session whenever possible, ask Secutix only for the details a page really needs, avoid repeated calls in the same journey. A 2024 release brought the login and sign-up journeys well under what they used to cost.
04
Make it a rule
Each call has a cost for the Opéra. Any new feature that touches Secutix now starts with a technical design approved by the Opéra.

Cache, one duration per kind of content

Varnish runs on each front server, for the site and for the API. Each API endpoint gets a cache duration that matches how often its content really changes:

LevelDurationExamples
None0 sAlerts, ticketing features
Very short60 sOne show, customer data, ticketing availability
Short15 minAll shows, all events, galas
Medium3 hMedia, free pages, home page features
Long6 hDigital stage content, magazine features
Very long24 hArtists, partners, magazine articles, seasons, venues
  • Cookies are stripped from cacheable requests, so one copy serves everyone.
  • Requests with a session or a back-office preview cookie skip the cache.
  • Editors can purge a page from the back office after a change.
  • A grace period lets Varnish serve the last good copy if the back end is slow or down.

Load tests

Before big sales openings and infrastructure changes, we ran load tests with the hosting provider and the Opéra.

01
Real journeys
Scenarios recorded in the browser with the Grafana k6 recorder, then scripted in k6: home page, show pages, login.
02
Ramp-up
Stages up to 700, then 1,000 concurrent virtual users, held for several minutes each.
03
Protect the ticketing
During the test, production points to the ticketing pre-production, with thousands of test accounts set up by the Opéra, so the real ticketing is never loaded.
04
Clear roles
Run early in the morning, outside business hours. The host runs the injection and watches the servers, the agency owns the code, the switch of ticketing endpoints and the maintenance page.
