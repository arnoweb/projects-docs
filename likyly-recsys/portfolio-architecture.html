LIKYLY // ARCHITECTURE

A multi-tenant recommendation API, installed with one npx command and integrated by the developer's own AI coding assistant through an MCP server.

Python · FastAPI PostgreSQL + pgvector Implicit ALS MLflow MCP Node.js wizard (npx)

What LIKYLY does

LIKYLY puts "you may also like" blocks on a site and learns from what visitors actually do. Each customer gets its own model, trained only on its own catalog and events.

Connect a catalog

Shopify, a REST API, a CSV or JSON URL, a webhook, or the WooCommerce connector. You choose which fields are used. Syncs are full, incremental or push.

Placements

A named recommendation block, such as "4 related products on a product page, no out-of-stock items". You configure it once and call it by name.

From the first pageview

Anonymous visitors get content-based and session recommendations. Logged-in users also get their history (collaborative and hybrid). The auto strategy picks the right one for each request.

Events & attribution

Impression, view, click, add to cart, purchase, or your own event types. Each answer has a recommendation_id, so you can see what each block earned.

Self-retraining models

A model retrains when enough new interactions come in. A new version goes live only if it does better than the one in production.

Integrate anywhere

8 official SDKs (JS/TS, PHP, Python, Java, .NET, Go, Ruby, Rust), React components and a WordPress connector, all generated from one OpenAPI contract.

A typical integration, in three steps

01
Connect the catalog
Create a data source, preview it, map the fields (identifier, text used for content, price, stock, image), then run a first sync.
02
Configure a placement
Choose how many items, the strategy and the filters. Then preview the result on real products before any code is written.
03
Integrate and validate
Add the block and its tracking events to the site. LIKYLY then checks from its own data that the integration works: requests and events actually arrive.

These three steps don't need a dashboard. The developer's AI assistant does them through the MCP server (see Developer experience).

One command, then the AI assistant does the work

Developer experience (DX) is part of the product. Like PostHog's install wizard, LIKYLY is installed from the terminal in one command. A visual dashboard is not needed:

$ npx @likyly/wizard

The wizard has an interactive terminal UI (Ink). At the end, it opens Claude Code (or Cursor) with an integration prompt. LIKYLY has no chat of its own: the developer's coding agent is the interface. It reads the project, calls LIKYLY's MCP tools and writes the integration into the codebase.

The wizard, step by step

01
Detect
Reads the framework from the project's own files (package.json, composer.json, pyproject.toml, go.mod, wp-config.php…) and the package manager already in use.
02
Review the plan
Shows every command and every file before anything happens. Nothing existing is overwritten. In a git repository it offers to work on a likyly/setup branch, and it never commits.
03
Install the SDK
@likyly/sdk, plus @likyly/react for React frameworks. The package manager's output is shown live.
04
Connect the account
Opens likyly.com to sign in. The keys come back to a one-time server on 127.0.0.1, protected by a random state. The public key is written under the name the framework exposes to the browser (NEXT_PUBLIC_LIKYLY_KEY, VITE_LIKYLY_KEY…). Secret keys are refused.
05
Connect the AI assistant
Writes the MCP configuration for Claude Code, Cursor and VS Code, plus the LIKYLY skill and slash commands. The configuration only refers to LIKYLY_DEVELOPER_KEY. The key itself stays in .likyly/credentials.env, which is ignored by git and readable only by the developer.
06
Verify, then hand over
Checks the SDK version, that the stack is supported, that the keys are accepted and that the assistants are connected. It lists the changes to review in git diff, then launches Claude Code with the integration prompt.

npx @likyly/wizard uninstall shows its plan, then removes everything the wizard added, on its own branch. It also has --dry-run and a non-interactive CI mode.

Prompts instead of documentation

Each integration step is one plain-language prompt. The agent chains the MCP tools it needs. If an MCP tool can give the information, the developer doesn't have to read the documentation.

PROMPT — CONNECT MY CATALOG "Connect my Shopify catalog to Likyly. Use product.id as the identifier, title and description for content, and pull price, categories, image and stock. Run a first sync." → list_source_types · create_data_source · test_data_source · preview_data_source · configure_field_mapping · sync_data_source · get_catalog_stats
PROMPT — CONFIGURE RECOMMENDATIONS "On a product page, show 4 recommendations. For an anonymous visitor, use the current product and the session. For a logged-in user, add their history. Exclude unavailable products." → create_placement (strategy auto, in_stock_only) · preview_placement · get_placement_requirements
PROMPT — INTEGRATE AND VALIDATE "Add the pdp-related placement to this React product page. Show 4 cards that match the existing design and add every event Likyly needs to learn." → get_integration_recipe · get_tracking_requirements · writes <LikylyRecommendations> + events · validate_integration

The agent always reads the repository first (framework, rendering mode, whether user context exists). It adapts the recipe to the real component instead of pasting a whole file. validate_integration then checks the result from LIKYLY's own data, not by guessing from the source code. /likyly-inventory and /likyly-model report what was added to the site and how the model performs (precision@10, version in production).

Runtime architecture

FIG. 2 — One API service and one database. Embeddings live in Postgres, so there is no separate vector database to run.

Recommendation pipeline

FIG. 3 — Two kinds of models, blended at request time.
01
Content-based
TF-IDF similarity combined with sentence-transformer embeddings (all-MiniLM-L12-v2, 384 dimensions) stored in pgvector. They are computed when a product is ingested, so a new product can be recommended right away.
02
Collaborative
Implicit ALS on real interactions: a purchase weighs more than a view. No made-up 1–5 star ratings.
03
Hybrid & session
A tunable alpha blends content and collaborative scores. Session mode recommends from recently viewed items, with no login.
04
Model governance
Retraining is triggered by interaction volume, not by a fixed schedule. MLflow tracks each run and DVC versions the artefacts. A new model goes live only if it beats the production version.
05
Cache
Anonymous answers for a product page are cached per placement. The cache empties itself when the placement or the catalog changes. Each call still gets its own recommendation_id, so attribution is not affected.

Keeping 8 SDKs correct

The OpenAPI document is the single source of truth. 43 shared request/response scenarios are checked against it, and every SDK's test suite replays them. The SDK READMEs and code samples are generated, and a CI check fails if they drift from the code. The test suite runs the real app against a real Postgres + pgvector.
